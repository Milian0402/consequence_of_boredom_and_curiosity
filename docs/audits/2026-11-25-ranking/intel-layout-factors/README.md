# Replay the 64-combination storage-layout study

The two implementations multiply the same signed FP32 inputs with three independent leading dimensions and three independent starting offsets. The 192 layouts comprise three historical geometries and all 64 combinations at each geometry. The resulting ratios express elapsed time. The study evaluated the consequences of changing specific layouts at fixed geometry.

From this extracted directory, run `python3 -B replay.py` with Python 3.9 or later. It checks the original artifact member hashes, source identities, 192 true kernel traces and four independent correctness fixtures per layout and method before regenerating every main effect, pair interaction, and the report. The full numeric input fingerprints can independently be regenerated by compiling `hash-fixtures.c` using a C11 compiler and ordinary IEEE FP32 semantics. A matching reference table is `logical-input-hashes.csv`.

The exact native benchmark directory is in `benchmark/`. `raw/` retains original numerical, source, CPU and route records. The provenance lists the checksum of each official archive member including build logs. The compact packet retains the build and timing identities needed for offline analysis. To rebuild an ordinary production executable, use the complete benchmark repository at revision `9e2483cc4b1839a2e0a392f2cfdb656d807d006e` and the production source `a30d71f0aaba4bcceb9ec5c530cffd63e6967cd6` specified in its workflow. The normal oneMKL interface used the sequential runtime. Reproducing timing requires equivalent native hardware and measurement conditions.

Each stored numerical CSV and the original Linux-derived score is preserved byte for byte. Statistical replay compares all discrete values exactly and allows four units in the last place for derived binary64 quantities. Linux and Darwin math libraries differed by at most 2.23×10⁻¹⁶ in the observed replay.
