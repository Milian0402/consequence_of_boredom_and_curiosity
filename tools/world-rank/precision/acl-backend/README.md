# Arm Compute Library BF16 component products

The backend calls Arm Compute Library v53.3.2’s compiled Advanced SIMD `a64_interleaved_bf16fp32_mmla_8x12` assembly kernel. Each multiply accepts two BF16 matrices with independent row strides and overwrites FP32 C. The common precision driver performs the FP32 input decomposition and combines the returned products. This method is vendor-assisted. [Pinned Arm SDK](https://github.com/ARM-software/ComputeLibrary/releases/tag/v53.3.2)

For each component product the backend repacks the current A and B into groups of four depth elements, zero-fills partial tiles, calls the original ELF symbol, and copies the live cells of 8×12 output tiles to the caller’s C. Up to eight tiles from each axis share a kernel call. Packed operand data is rebuilt on every execution, including repeated uses of a plan with new data. Linux HWCAP must advertise ASIMD and BF16. The backend verifies that the resolved symbol belongs to the pinned ELF and the native measurement checks one process thread and CPU affinity.

A successful plan performs two allocations. For M×N×K let A and B be the counts of eight-row and twelve-column tiles and let Kp be K rounded up to four. One block holds the 96-byte plan. The other holds `16*A*Kp + 24*B*Kp + 384*min(A,8)*min(B,8)` bytes of A packing, B packing and partial C storage. The assembly kernel uses its own stack frame. The shared precision driver additionally allocates its FP32/BF16 input planes and output accumulation workspace. Its raw single-product mode creates three driver allocations and one backend plan, five allocations total. Its ordinary 3/6/9-term modes create four driver allocations and one plan, six allocations total. The three-band six-term mode has five driver allocations plus three sequential plans for depths 3K, 2K and K, eleven allocations in total. These counts cover successful normal component paths.

Run `bash build.sh VENDOR_DIR OUT [pinned-archive.tar.gz]` on Linux AArch64. Link the ordinary core to `libacl_bf16_backend.so`, with OUT on its runtime library path. The build pins both the SDK archive and the distributed ELF, disassembles the actual named symbol, and records all code identities. The trace library uses GNU link wrapping at the real kernel boundary to validate packed pointers, strides, tile counts and scratch bounds and to report the number of observed calls. The ordinary library directly imports the original Arm kernel. Run `python3 qualify.py OUT proof.json M N K LDA LDB LDC` under a pinned CPU to qualify a layout; both builds check all FP32 outputs, changed input buffers and guards.
